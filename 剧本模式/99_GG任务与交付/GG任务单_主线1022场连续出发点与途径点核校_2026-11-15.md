# GG 任务单：主线 1022 场连续出发点与途径点核校（2026-11-15）

## 一、核心原则（连贯故事 · 前后衔接）

主人要求：**这是一个连贯的完整故事，每一场必须结合「上一场（`prevEvent`）」和「下一场（`nextEvent`）」连续推算**，确保出发点与每个途径点在地理顺序和史实上完全顺畅、绝不瞬移或折返。

### 两种情况的衔接规则
1. **同一武将连战（`prevEvent.isSameGeneral === true`）**：
   - 军团实际从**上一场战场（`prevEvent.placeName` / 经纬度）**继续出发！
   - `route` 必须严格按照 **`prevEvent` 终点 → 途径点[0] → 途径点[1] → … → 本场 `targetName`** 的真实行军方向排列。
   - **严禁**把途经点按武将老家首都重新走一遍，也**严禁**把 `prevEvent` 终点或本场 `targetName` 重复放进 `route`。
   - 同时核对本场结束位置能否自然衔接 `nextEvent`（若 `nextEvent.isSameGeneral === true`）。
2. **换人接棒首战（`prevEvent === null` 或 `prevEvent.isSameGeneral === false`）**：
   - 必须核实 `currentFromName`（出发据点 `fromCityId`）是否为该武将**此战史实真实的出发据点**（严禁误用战后定都地或成名地，如韩信打潍水不能从临淄出发、李世民打虎牢关不能从虎牢关出发、刘备打雒城不能从成都出发）。
   - 若 `currentFromCityId` 有误（尤其是带 `NO_EXPLICIT_FROM` 或 `FROM_NEAR_TARGET_WITH_ROUTE` 标记的），必须在 `fixedFromName` / `fixedFromCityId` 中指明正确出发据点（优先选用 `src/data/cities_v2.ts` 中已有据点名称），并同步给出从该新出发点到 `targetName` 的正确 `fixedRoute`。
   - 若为**守城战且随行守方**（`battleType === "siege" && role === "defender"`）：如本就在城内守城，`fixedRoute` 应为 `[]`。

## 三、输出格式要求

每批输出 JSON 数组，**逐场覆盖该批全部场次**（不得跳场）：

```json
[
  {
    "seq": 1,
    "eventId": "evt_0001",
    "status": "ok",
    "fixedFromName": "波斯波利斯",
    "fixedFromCityId": "city_bosibolisi",
    "fixedRoute": [],
    "reason": "开卷首战，守城/迎战于帕萨尔加德，衔接正常",
    "source": "那波尼德编年史；希罗多德《历史》1.127"
  }
]
```

- `status`：`"ok"`（原出发点与途径点均连贯合理，沿用原值）或 `"fixed"`（修正了 `fixedFromName` / `fixedFromCityId` 或 `fixedRoute`）。
- 无论 `"ok"` 还是 `"fixed"`，均请保留完整的 `fixedFromName`、`fixedFromCityId`（若无改动则照抄原 `currentFromName`/`currentFromCityId`）与 `fixedRoute`（纯地名 + `{ name, lat, lng }`，不含起点与终点），方便脚本一键回写。
- `reason` 须写明与上一场/下一场的衔接判断依据（尤其 `status === "fixed"` 时）。
