## 二、产品目标与边界

- 这是直播游戏，不是普通单机游戏，也不是每个观众各控一个角色。
- **所有观众共同操作同一个“玩家”**。玩家本人的成长、官职、军团和战略行为，就是直播间的公共进度。
- 九官职是**这个公共玩家的官职**，不是每个观众各自有一套官职。
- 核心交付不是聊天机器人，而是一套完整的**直播输入 → 决策仲裁 → 玩家动作执行 → 状态保存 → 画面反馈**控制技术。
- 优先目标：尽快跑通**一个平台、一个直播间、一条可收费且可恢复的完整链路**，以实际收入和内容传播为主，不先追求多平台或大规模云架构。
- 积分和真钱是两种不同账目：积分用于推动观看、互动和选择；真钱用于明确的付费效果。不得把二者混成一种余额。
- 普通聊天不宜直接送积分；积分增长应与新增点赞、订阅增长、在线新高等传播目标挂钩，并明确奖励对象和防刷规则。
- 主播希望能够限制只有订阅者参与免费游戏指令；需要另行核实付费事件是否也受该限制，不能混为一谈。
- 玩家技与武将技必须分开，付费后必须“确实厉害”，但不要求机械地等于“属性乘十”。

## 核心审查：观众操作公共玩家的控制技术

这是本任务最重要的部分，应投入最多篇幅。必须给出一条真正能落地的控制链，而不是只写“读取弹幕然后调用游戏”。

### A. 先比较三种操作方式

1. **直播聊天指令**：观众直接发口令。评估进入门槛、延迟、误输入、刷屏、可读性和平台支持。
2. **独立网页控制器**：观众在网页按钮、列表和地图上操作。评估是否真的更低延迟、账号绑定、公网部署、作弊防护，以及观众离开直播画面的成本。
3. **平台官方互动扩展**：若平台支持，评估按钮式互动、身份验证、开发审核和地区限制；没有官方能力就明确没有，不能假设。

最后明确：首个单平台演示应以哪一种为主，另外两种为什么现在用或不用。不要默认聊天一定最好，也不要为了界面漂亮强推独立网页。

### B. 给出统一控制协议

无论输入来自聊天、付款留言还是以后的网页按钮，都应归一化为一种命令。至少说明这些字段如何产生和使用：

- 平台事件唯一 ID；
- 观众稳定账号 ID（不能用可重复的显示名当身份）；
- 显示名及其审核状态；
- 命令类型与结构化参数；
- 积分出价、真钱事件及各自账目；
- 平台发布时间、本机接收时间；
- 当前直播场次与战斗场次；
- 队列序号、处理状态和失败原因。

原始聊天只负责输入，**不得直接修改玩家、军队、武将或账本**。先通过统一命令层，再进入游戏执行层。

### C. 把控制链逐层画清楚

至少覆盖以下七层，并指出当前代码分别在哪里：

1. **输入适配层**：接收聊天与付费事件，去重，保留原始记录。
2. **命令解析层**：把文本或网页输入变成结构化命令，拒绝无法识别和过期输入。
3. **权限校验层**：根据公共玩家当前官职、所在势力、文化、战斗状态、目标合法性判断能否执行。
4. **仲裁与账本层**：积分/真钱分账，竞价排序，同价先后，扣款或托管，防重复执行。
5. **持久队列层**：已接受但未执行的动作必须跨刷新、断线、重启保留；明确 ACK 是“已持久接受”还是“已实际释放”。
6. **游戏执行层**：调用明确的游戏接口，真正执行投靠、移动、选目标、放玩家技、建军、合军、臣服等动作。
7. **反馈与恢复层**：直播画面能看出谁做了什么、当前队列和结果；失败、取消、过期、战斗结束时按规则退款或作废。

必须画出文本数据流图，并标出**唯一权威状态**在哪里。浏览器缓存、Node 账本和战场状态不能各自成为一套互相冲突的真相。

## 五、主人给出的九官职规则（规则原文的整理版）

### 通用规则

- 九阶段靠功劳晋升。
- **离开势力功劳清零，但官职保留。**
- 玩家就是全体观众共同操作的同一角色。
- 观众通过某种方式获得积分，并在不同官职用积分做选择。
- 玩家技的竞价顺序：例如张三出 3 分先放，李四只能之后同样出 3 分后放，或出 4 分先放；同价按先后，高价可插队。
- 元帅选择攻击目标也采用类似的先后与积分竞价规则。
- 玩家技不等于武将技，不能简单做成“全军属性乘十”，但付费后必须有明显、可靠的效果。

| 官职 | 战术能力 | 战略与直播权限 |
|---|---|---|
| 平民 | 只能在战略地图上活动，自动去投靠武将 | 玩家名字可用积分竞拍，出价最高者可改玩家名字 |
| 斥候 | 释放玩家技，强化玩家本人，达到很强的个人效果 | 离开势力后，可选择与上一次相同文化的所有势力加入 |
| 探马 | 玩家技扩展到玩家所在本队 | 离开势力后，可选择与上一次相同文化的势力武将加入 |
| 先锋 | 玩家技扩展到本排 | 离开势力后，可选择所有势力加入 |
| 将军 | 玩家技扩展到本军 | 离开势力后，可选择所有武将加入 |
| 元帅 | 拥有以上能力 | 可用积分竞价选择军队攻击目标；可挑选立绘：先选文化，再从该文化随机 4 或 5 张中选 |
| 公侯 | 拥有以上能力 | 建立自己的势力名字，成为与主公同盟的独立势力；势力名可竞拍，旗号由玩家决定一个字；可从收集兵模中组建并命名三排军团；以后每打败一种有新兵模的军队一次获得一个兵模；据点从本势力据点之一中选择，选择可竞拍 |
| 国王 | 拥有以上能力 | 据点和兵力都大于主公三倍时，可让本势力其他武将领军加入；必须符合出兵条件；加入后合并为一支军队、兵力相加，战术模式加入武将可自动放武将技 |
| 皇帝 | 拥有以上能力 | 可让据点和兵力都小于自己十倍的势力臣服；只能威压领土接壤势力；消耗巨大积分，一次只能一个，不能频繁发生；臣服后可将该势力武将按出兵条件并入军队 |

### 起名与审核

- 玩家名、势力名、军团名等都必须有字数限制和屏蔽词表。
- 主播必须有一键否决能力，避免恶意名字导致频道受处罚。
- 请继续检查：审核前是否允许上屏、否决后恢复什么名字、是否退款、是否需要冷却和改名记录。

### 合军与技能

- 合军后兵力相加，加入武将可自动放技。
- **主将光环只计算一次。**
- **所有武将技共用释放间隔。**
- 玩家技继续独立结算，不得借合军重复套光环或绕过技能间隔。

## 六、逐项检查规则闭环

请把九官职整理成“官职 × 观众权限 × 决策方式 × 积分价格 × 队列/冷却 × 失败处理”的完整表，并检查：

4. **竞价规则**：积分如何托管、何时扣除、被插队是否退款、同价平局、离线出价、反抢价、冷却和上限是什么？指出缺失，不要擅自替主人定新规则。
5. **技能范围**：本人、本队、本排、本军的“队/排/军”是否复用现有编队关系，而不是按兵模名字或临时距离猜。
6. **技能效果**：强度是否足够且可读；持续叠加、晋升换范围、阵亡、复活、战斗结束和未释放退款是否有漏洞。
7. **元帅选目标**：选择何时生效、能否改已开始战斗的目标、目标失效怎么办、观众竞价与游戏 AI 谁优先。
8. **公侯独立势力**：与主公同盟是否允许 later 解盟；据点不够、主公灭亡、旗号重复、军团无兵模时如何处理。
9. **兵模收集**：判定“新兵模”的唯一键是什么，同一军队重复刷、败北、撤退、武将重复、跨周目是否给。
10. **国王门槛**：“据点和兵力都大于主公三倍”是否两项同时满足，主公不存在时怎么办。
11. **皇帝威压**：“小于自己十倍”是否指目标两项都不到自己的十分之一；接壤按实际领土还是据点邻接；臣服后的忠诚、解除和连锁臣服是否缺少约束。
12. **付费与公平**：是否出现一个人用真钱永久霸占所有选择，免费积分是否仍有实际作用，直播间新观众能否理解并参与。
13. **审核安全**：任何观众可控文字是否默认先审后显；一键否决是否覆盖战略界面、战术界面、直播回放和语音播报。

## 八、最终输出格式

严格按以下顺序交付：

### 1. 一句话结论

采用什么观众操作方式 + 什么控制链 + 当前距离“观众可靠操作公共玩家”还差几步。

### 2. 观众操作技术与统一控制协议

比较聊天、独立网页、官方扩展；给出唯一首选操作方式、命令字段和完整文本数据流图。

### 3. 九官职动作执行矩阵

逐个列出所有操作的输入、权限、仲裁、真实游戏接口、持久化、失败退款和当前实现状态。每项标记：**已实现 / 部分实现 / 未实现 / 与规则冲突 / 只能实测确认**，并附 `文件:行号`。

### 4. 仲裁、账务与只执行一次证明

用具体时序说明竞价、扣款、入队、ACK、执行、恢复和退款；列出重复事件、多页面、旧命令、目标失效等情况为什么安全，或指出哪里不安全。

### 5. 平台对比与唯一选择

官方证据表、首选、备选、决定性理由、真实试播风险。平台是控制链的输入通道，不得让平台比较盖过玩家动作执行技术。

### 6. 九官职完整规则表

每级能做什么、谁决定、积分如何竞价、何时扣退、有什么冷却与限制。

### 7. 问题清单与整改顺序

按 **P0 无法可靠操作或阻断收费、P1 破坏规则或账务、P2 体验与扩展** 排序。每项写：问题、证据、影响、最小修法、验收方法。

### 8. 最小验收剧本

只验一个平台，依次覆盖：

1. 官方直播与聊天室连接；
2. 订阅账号发出指令后，公共玩家真正执行动作，而不只是收到日志；
3. 一笔真实付费事件驱动一次技能；
4. 非订阅账号付费行为（若文档未明确）；
5. 竞价顺序与同价顺序；
6. 技能实际生效且不污染武将技；
7. 投靠、选目标等至少一种战略动作真正改变游戏状态；
8. 刷新、断线、重启、多页面接管；
9. 未释放退款与已释放不退款；
10. 恶意名字拦截和主播一键否决。

### 9. 真正需要主人决定的问题

只列规则冲突或规则未覆盖的问题；已有明确规则的，直接按规则判断，不反问主人。

## 九、检查原则

- 先证明观众能操作玩家，再核实输入平台，再对规则，最后看代码。
- 证据不足就写“未验证”，不要补成确定事实。
- 不要把“能收到弹幕”当成“能稳定收费”。
- 不要把“本地测试通过”当成“真实直播跑通”。
- 不要为了多平台、云架构或微服务而推翻适合单直播间的简单方案。
- 不要擅自修改主人规则，不要把设计取舍反丢给主人。
- 最重要的判断标准是：**能否让一个新观众看懂、参与、愿意付费，并让主播安全地持续开播。**
