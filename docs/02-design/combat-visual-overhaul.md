## 1. 背景方案：zoom 13 微观特写

### 决策
- **千军万马画面使用 zoom 13**（战场中心），作为 8/9/10 之外的**演出视角**。
- zoom 10 自动战斗观感（城图放大 410px、9 兵牌、攻城器械）**完整保留**，作为战斗入场/概览。
- 备选降级：若 Phase 0 实测 13 级瓦片过糊 → 降级 **zoom 12**（11 级瓦片放大 2 倍）。

### 依据（代码确认）
| 项 | 数值 | 出处 |
|---|---|---|
| 本地瓦片最高真档 | zoom 11（`maxNativeZoom: 11`） | `GameMap.ts:321` |
| 13 级瓦片 | 11 级放大 4 倍 + Hillshade 真山体（terrarium 到 z18） | `HillshadeLayer.ts:218` |
| 攻城圈直径 @13 | 0.1° ≈ 1164px（@10 仅 146px） | 364×2⁴ px/° |
| 300 精灵方阵（32px 步距 15×20） | 480×640px | 3 万兵 = 300 精灵 |
| 空间结论 | **@10 放不下（146px 圈 vs 480px 阵）；@13 从容** | 实测公式 |

### 风险：Phase 0 实验（开工第一件事）
1. 手动飞 zoom 13 截图：瓦片糊不糊、古纸滤镜下是否可接受。
2. 测 Hillshade 重建耗时（zFactor 12/13 = 45/50 会触发全量重建；可统一 8–13 = 30 消除）。
3. 测帧率（滚动/静止）。

### P0 已产出（数学部分，2026-08-09 `scratch/p0_zoom13_math.mts` 实测）

| 项 | 实数 | 结论 |
|---|---|---|
| 瓦片请求量 | 底图 **0 新请求**（11 级缓存放大）；Hillshade **30 块** AWS + 预取 45 块 | 首屏 ~1–2s（3 Worker 池） |
| 空间验算 | 单阵 360×450px；**5 万兵以内 1920 屏内放得下**（3 万兵 = 4 阵 1700px 含城） | ✅ 300 精灵=3.7→4 阵（3 满 1 残） |
| 兵牌 scale | **zoom 13 单独档 ≈ 0.90**（38px 兵牌）；2^(zoom-9) 公式 11.2 荒谬 | ✅ 需单独定档 |
| 位置关系 | 方案 B：**阵心距城心 280px**（城图半宽 70 + 阵半宽 180 + 间隙 30）→ 前排贴城墙外沿；方案 A（阵心在攻城圈 582px 处）❌ 太空 | P1 实测微调 |
| 性能预算 | 3 万 vs 3 万 = 600 精灵 × 60fps = 36000 drawImage/s | ✅ 余量充足 |

> ⚠️ 修正：COMBAT_RADIUS 0.1° = 582px @13 是**半径**（非直径）；3 万兵 = 300 精灵 = **4 个 9×9 阵**（非 3 阵），阵排布（一字 vs 2×2）P1 定。

> ⏳ 待视觉验证（浏览器 daemon 故障，需主人本机确认）：13 级瓦片糊不糊、Hillshade 实际延迟、帧率。命令：dev server 已启动，浏览器开 `http://localhost:5173/`，F12 控制台执行 `gameMap.flyTo({lat:34.27, lng:108.93}, 2, {zoom:13})`。

### 补充实测：zoom 13 的三条独立佐证（2026-08-09 代码核查）

**佐证一：城池美术到 13 都不会糊。** 公式 `getSiegeCityScreenWidthPx`（`city-marker-tokens.ts`），
原图 1024×765：

| zoom | 攻城态城池屏幕宽 | 占原图 | Google Terrain 底图 |
|------|----------------|-------|------------------|
| 10（现状） | 410px | 40% | 原生锐利 |
| 11 | 546px | 53% | 原生锐利 |
| 12 | 683px | 67% | 2 倍拉伸 |
| 13 | 819px | 80% | 4 倍拉伸 |

> **画面主体永远在原图 1024px 之内，从不被放大插值**。会糊的只有背景底图。

**佐证二：13 是第一个"独占舞台"的档位。** 据点间距审计（`npm run city:spacing`）：
922 座城、最小间距 **50km 硬顶**、违规 0 对。视野宽度每升一档减半，
zoom 13 视野约为 zoom 10 的 1/8。低于 13 会有邻城挤进画面，且邻城按正常小尺寸显示，
一大一小并排会破坏"千军万马围一城"的场面感。

**佐证三：山体阴影在 13 级是原生精度，不跟着底图糊。**
`HillshadeLayer` 按当前 zoom 直接请求 terrarium 高程瓦片
（`HillshadeLayer.ts:332` `.../terrarium/${coords.z}/${x}/${y}.png`），
不受 `maxNativeZoom: 11` 限制。**所以 13 级地形起伏反而比 10 级更细**，
糊的只有底图的色彩纹理。这让"13 级太糊"的担忧显著小于预期。
> 代价：13 级瓦片数量更多 → AWS 请求量与 worker 池压力上升，Phase 0 需一并测延迟。

### 待定：13 级特写时城池是否保持放大态

§3 现写"13 特写时城图**不放大**（正常 100–140px）"。两种做法的实际屏幕宽：

| 做法 | zoom 13 城池屏幕宽 | 观感 |
|------|-----------------|------|
| 保持攻城放大态 | **819px** | 城墙压迫感强、电影感，但留给军阵的横向空间少 |
| 关掉放大（现文档写法） | 约 420px（140 底宽 × pane 3.0） | 军阵舒展，城池退为背景 |

两者都成立，取决于要"城为主、兵为辅"还是"兵为主、城为景"。**建议 Phase 0 两版各截一张对比。**

## 2. 表现方案：双将战的"兵"微观化 — **2026-08-09 主人定稿（先做兵，城/建筑全剥离）**

> **范围（2026-08-09 主人三连收敛）**：**无论野战还是攻城战，只做武将 VS 武将（双将战）**；
> **先不做城池、建筑、城墙**——只做"兵"（N 精灵方阵 + 自动战斗）。
> 城/建筑/攻城圈/外推等全部后置，等"兵"跑通再套场景。
> 画面 = 很多精灵图自动战斗（帝国时代 / 三国群英传小兵观感）。

### 2.1 核心结构：双将战 9×9 大方阵（仅 zoom 13）

| 项 | 设计 | 状态 |
|---|---|---|
| 方阵规模 | **9×9（81 精灵 ≈ 1 万人/阵）**；按兵力 N 阵（3 万兵 = 4 阵） | ✅ 主人定 |
| 兵力映射 | 方阵数 ≈ troops / 10000，每阵 81 精灵（1 精灵 = 100 兵） | ✅ |
| 兵种分层 | **9×9 内三排分区：前 3 排枪兵 / 中 3 排步兵 / 后 3 排弓弩** | ✅ 主人定 |
| 方向 | 按战略地图真实分布（军团真实朝向，现有方向数据延续） | ✅ |
| 动画 | 推进 = MOVE 帧；前排接敌 = ATTACK 帧循环；死亡 = DEATH 帧 + 白烟 | ✅ |
| 兵力削减 | 存活精灵数随 troops 每秒同步；前排优先死亡，后排前压 | 待 P2 定 |
| LOD | **zoom ≥ 13 渲染 N 精灵；zoom < 13 保持 9 兵牌** | ✅ |

### 2.2 待实测参数（P1 实验定死）

- zoom 13 兵牌 scale（baseHeight=75 基准 → 目标 ~38px → **microScale ≈ 0.5**）
- 精灵间距 / 行距（9×9 阵宽 ~360px 目标 → spacingX ≈ 1.2、spacingY ≈ 1.35）
- 两阵/军团间距（交战间隙）

### 2.3 明确不做（本期）

城池、建筑、城墙、攻城圈/外推适配、独立个体模式（散兵）、三幕动画模板。城/建筑等"兵"跑通后按场景（野战→攻城）再套。

## 3. 切换机制（9/10 ↔ 13）

```
战斗开始（跟拍军团进入交战）
   ├─ ① zoom 10（现有逻辑，1~2 秒）—— 战场全景：城图放大、器械、9 兵牌
   ├─ ② 自动 flyTo 战场中心 zoom 13 —— 千军万马演出（城图不放大，方阵列阵）
   ├─ ③ 演出期间：13 为主；玩家可切回 10 概览再进
   └─ ④ 战斗结束 → 回 9（现有逻辑）
```

- ZoomController 新增"演出模式"状态：13 期间暂停自动切 zoom，退出恢复。**8/9/10 自动逻辑不改。**
- 玩家手动滚轮随时可看，不强制。
- 13 特写时城图**不放大**（正常 100–140px），退出恢复放大态。
- **LOD 切换点 = zoom 13 落地**：`zoom < 13` 保持 9 兵牌（现有），`zoom ≥ 13` 自动切 9×9 多阵（81 精灵/阵）——渲染器按 zoom 阈值自动切，不手动干预；切换做 ~0.3s 淡入淡出过渡，避免"啪一下变多"。
- **🔴 13 演出触发条件（2026-08-09 主人定）**：① **跟拍军团参与的战斗**（非跟拍战斗不微观化，全图性能命门）② **双将战**（攻守双方都有指挥官）③ **野战先行**（本期做野战；攻城后置，跑通后再套）。三条齐备才进 13（自动飞 13 + 大方阵渲染）；**否则保持现状**（zoom 10、9 兵牌）。判定复用引擎双将逻辑（commander 存在性）。

## 6. 性能约束

| 约束 | 规则 |
|---|---|
| 微观化范围 | **只对跟拍战斗双方**；全图其他军团保持 3×3/123 兵牌 |
| 精灵预算 | 3万 vs 3万 = 600 drawImage/帧 —— **"无压力"属未实测推断，须由 P0 出实数**（见下方风险） |
| 动画帧 | 复用现有 IDLE/MOVE/ATTACK/DAMAGE/DEATH 帧 + FactionTintSystem 染色 |
| 假位移 | 渲染层位移必须 lerp 平滑，禁止瞬移（现有外推先例） |

> **「微观化范围」这条是整个方案的性能命门，务必守住。**
> `GlobalUnitRenderer` 画的是**视野内全部军团**。若精灵数跟兵力挂钩却不分 zoom，
> 行军 zoom 9 下每支路过的军团都会从 9 个膨胀到几百个——20 支军团即数千精灵，
> 而这是**每时每刻都在发生**的常态场景，比只有几十秒的战斗危险得多。
> 本文档已用"只对跟拍战斗双方微观化"堵住这个口子，实现时不可放宽。
>
> **P0 必须产出的实数**（不实测不进 P1，数字决定精灵尺寸/帧数/图集规格，定错全套美术返工）：
> 1. 本机（GTX 1660 Ti）Canvas 2D 在 60fps 下的 drawImage 精灵上限
> 2. 叠加已知性能债后的余量：矢量层重投影导致缩放冻结 360ms、跟拍 85ms/秒
> 3. zoom 13 下 Hillshade 的 AWS 瓦片请求量与 worker 池延迟
