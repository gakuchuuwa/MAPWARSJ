# 战争编年史 · 自动推进设计方案（2026-11-12）

> 一句话：**编年史不是第四种模式，而是百岁模式里的「导演层」**。它只回答五个问题：
> **下一件事是谁、在哪、哪一年、念哪两段、打完接谁**。
> 走路、寻路、会面、起兵、开战、战术演出、两段播报，全部复用现有经典战管线，不另写一套战斗。

## 〇、总方针（2026-11-13 主人定；与下文旧稿冲突处以本节为准）

### 五方针

1. **单一真源**：编年史 json 是事件的唯一来源（顺序、年份、地点、随行主将、两段播报）。游戏数据一律由导入脚本生成，生成文件禁止手改；发现错误只改 json，再重新导入。
2. **逐层定稿、逐层冻结**：事件 → 据点（**只有新增据点才需主人画路**）→ 武将（**势力、生卒年、精锐、军团齐全**，主人才能画立绘）→ 立绘（主人）→ 镜头与播报演出。上层定稿后再改，须主人同意，并重跑下游检查。
3. **第一卷做样板**：第一卷（前 550—前 500）每一场都能走完「找人 → 战略播报 → 开战 → 战术播报 → 交棒」后，踩过的坑写进检查清单，后续各卷照样板复制。
4. **验收**：每层一个检查脚本，全绿才算完成；开篇前 10 分钟由主人看录屏拍板。
5. **规则只写一处**：`AGENTS.md` ＋ 本页；新旧冲突当场删旧。

### 推演规则

- 编年史是百岁模式的导演层，**取消「1 分钟 1 年」自动时钟**，年份只在事件之间跳转；无事件年份直接跳过。
- **跟谁、离开谁只看事件的「随行主将」**，与胜负无关：下一场还是同一人 → 继续随军；换人 → 辞别离营，去找下一位。
- 每次跳年，据点归属、在场武将按当年史实重算；**战斗胜负只影响积分与功劳，不改据点归属**；后台 AI 军团不改据点归属。
- 观众在历史推演中只可在战术战场放计；其余控将口令只在乱斗模式受理。

### 事件收录标准（四条全满足）

1. 史有明年；2. 至少一方主将实名（另一方史失其名可留，禁编名）；3. 够分量（政权存亡、疆域易手、名将代表战、史书专载的会战 / 攻城）；4. 能落到地图上：50 公里内归库内据点；50 公里外先归 100 公里内据点作代表；再远申请新建战场。同一场战争 / 同一时期反复争夺同一据点，只留最知名一场。不凑年。

排序等级：**S** 改变世界格局的决战（主线必播）｜**A** 政权存亡、疆域大幅易手（主线）｜**B** 名将代表战、专载会战（主线，可取舍）｜**C** 影响较小（支线备选）。

### 称呼

势力可用后世通称防重名（东晋、北魏、东罗马）；地名、官爵用当时称呼；禁「古城 / 古都 / 旧都」、近代词（丝路、解放、抗战、中世纪、希腊化）与后人结局词。

## 〇.5、先给结论（2026-11-12 旧稿，冲突处以〇节为准）

1. **不新增 `autoPlan` 第四种模式**。在 `autoPlan === 'centenarian'`（默认百岁）里加 `ChronicleDirector`；新局默认开启，面板可暂停。理由：全项目已有大量 `autoPlan === 'centenarian'` 判定（据点归属、登场武将、旗号、马匹、建城年），再加一个模式会把它们全部改一遍。
2. **数据先行，每段一份 TS**。第一段 79 事件、11 棒，按事件类型粗分 **44 战 + 35 叙事**。
3. **时序**：事件级跳年（`GameApp.jumpToYear` 现成）；同一棒内连续行军；换棒/跨大区才允许「史书翻页」硬转场；战略段在出发前开念，战术段在开战/落地时念。
4. **先跑通再补全**：20 场能直接落到现有经典战 id + 35 场叙事 = **55/79 可以先跑**；18 场亚历山大剧本场景、6 场缺战斗数据先按叙事推进，补数据后再转战斗。
5. **两个必须先拍板的决策**：
   - **时间轴 -500 → -550**（否则第一段前 50 年 16 个事件会被 `jumpToYear` 钳掉）；
   - **缺战斗补不补**（9 位缺库主角已于 2026-11-12 补入；5、6 棒等仍缺战役数据）。

> **为什么不用现有剧本模式？** 剧本模式是**全局模式**：世界不募兵、军团不随机寻敌、事件按战场链走、打完转乱斗，本质是「一个剧本一场战役」。编年史要跨 16 段、117 棒、多个时代，还要保留百岁模式的自由世界与武将登场/退场。所以做**导演层**，不动世界规则。

## 二、数据契约（先改表，再写代码）

### 2.1 每段一份 TS

```ts
// src/data/chronicle/ChronicleTypes.ts
export type ChronicleKind = 'battle' | 'operation';

export interface ChronicleBattleStep {
    /** 事件内顺序（1..n） */
    order: number;
    /** 现有经典战 id（含隐式 generalId）；没有就空，整个事件按 operation */
    battleId?: string;
    /** 本棒主角在这一战站哪边 */
    role: 'attacker' | 'defender';
    /** 事件内这一战的名称（审计用，不上屏） */
    label: string;
    /** 这一战念「事件的战术段」，还是念「这一战自己的战术段」 */
    briefing: 'event' | 'battle';
}

export interface ChroniclePlace {
    /** 古典地名（播报用）：撒狄、巴克特拉、药杀水 */
    name: string;
    /** 运行时锚点：已有据点 / 已有战场 / 坐标，至少一个 */
    cityId?: string;
    battlefieldId?: string;
    lat?: number;
    lng?: number;
}

export interface ChronicleEvent {
    id: string;                     // chron_01_01_01
    segment: number;                // 1..16
    baton: number;                  // 1..117（「第1→2棒」归一化后取起始棒）
    relay?: { from?: string; to?: string };  // 交接事件：历史主角 from → to
    year: number;                   // -550
    season: 0 | 1 | 2 | 3;          // 春0 夏1 秋2 冬3
    month?: number;                 // 同年排序
    kind: ChronicleKind;
    rawType: string;                // 原「事件类型」，只作审计
    title: string;
    place: ChroniclePlace;
    /** 历史主角：镜头跟着谁（可缺库；缺库时用 cameraGeneralId 代理） */
    leadGeneralId: string;
    /** 实际出镜/带兵：优先 battleId 的 generalId，否则 leadGeneralId，否则代理 */
    cameraGeneralId?: string;
    enemyGeneralIds?: string[];
    enemyFactionId?: string;
    battles: ChronicleBattleStep[];
    /** 一段一屏；可多段（空行分段），与现有 announceBriefing 同口径 */
    strategic: string[];
    tactical: string[];
    source: string;
    sourceUrl?: string;
    note?: string;
}

export interface ChronicleSegment {
    id: number;
    title: string;
    fromYear: number;
    toYear: number;
    status: 'draft' | 'ready' | 'playable';
    events: ChronicleEvent[];
}
```

### 2.2 xlsx 必须新增的三列

| 新列 | 写法 | 为什么 |
|---|---|---|
| `leadGeneralId` | `ailan_julushi`；缺库写 `MISSING:哈尔帕古斯` | 散文链不能稳定解析主将 |
| `placeRef` | `city:city_sifaerde` / `bf:bf_xxx` / `lat,lng` / `MISSING` | 播报名与运行时锚点分离 |
| `battleSteps` | `ailan_julushi@-550|attacker|event`；多条用 `;` | 「关联经典战ID」是候选清单，不是顺序 |

> 这三列不加，导入器只能猜；猜错就会出现「亚历山大不在场、大流士在打」这种硬错。
>
> 定位口径：`battle` 事件的战斗坐标以 `battleSteps[].battleId` 对应 `GeneralFirstBattle` 的 `targetLat/Lng`/`targetCityId` 为准；`place` 只负责地图镜头与播报地名。`operation` 事件没有战斗，才用 `place` 定位。

### 2.3 事件分类规则

- `battle`：事件类型含 野战/攻城/守城/水战/关隘/两栖/平叛/光复/围城/受降/袭城/决战/会战，且 `battles[]` 至少一条能解析（或明确列为「待补战斗」）。
- `operation`：远征/使节/政变/交棒/筑城/航海/工程/撤退/整编/谢幕，或 `battles[]` 为空。
- `relay` 不是第三种类型，是 `battle`/`operation` 都可带的交接标记。

### 2.4 数据生产流程

```
xlsx（每段一份）
  → tools/chronicle/import.mts
      · 先套「AI改名与实体对齐清单」（表内 34 条数据）
      · 校验：89–144 字、零括号、零阿拉伯数字、零兵力数字、零「古城/古都/旧都」、零第二人称
      · 解析 leadGeneralId / placeRef / battleSteps；解析不了就报错，不猜
      · 写 src/data/chronicle/ChronicleSegmentNN.ts
      · 出审计报告 + 缺数据清单
  → tools/chronicle/audit.mts（0 错误才允许 status: 'ready'）
```

**不做**：不手写 79 条 TS；不因为缺数据就编造战斗/武将；缺就报缺，先用 operation 推进。

### 2.5 三名治（lead / camera / battle）

编年史的「历史主角」与「能打的武将」不一定同一人。明确三层：

- `leadGeneralId`：史书主角（客蒙、伯里克利…），可以缺库；播报念他的名字。
- `battleGeneralId`：`battles[].battleId` 对应的 `GeneralFirstBattle.generalId`，必须在库，用于起兵/战术模式。
- `cameraGeneralId`：玩家镜头实际跟的军团长。取序：
  1. `battleGeneralId`（有仗打，跟打仗的人）
  2. `leadGeneralId`（在库，跟史书主角）
  3. 同势力/同城/战场上的现有名将（代理）
  4. 无 → 纯 operation，玩家自己走

这样「客蒙缺库」不会阻断第 5 棒：播报照念客蒙，镜头跟同城/同势力的现有武将；等客蒙补进库，只改 `leadGeneralId`，代码不动。

**战斗与主角不同人时必须显式登记**：`battleSteps[]` 里每条都要写清 `battleId` 与 `role`；同一 `battleName|year` 在一个事件内只允许一条（攻守双视角按 `leadGeneralId` 选一边），跨事件也不得重复。审计对「`battleGeneralId !== leadGeneralId`」的条目逐条列出，必须能在事件标题/接力链里找到该将，否则报错。

## 三、导演器（ChronicleDirector）

### 3.1 职责边界

只做四件事：

1. 决定下一事件（顺序、年份、季节）。
2. 决定镜头主角与起点（事件地点 / 上一战落点 / 主角本城）。
3. 把战略/战术文案交给现有播报管线。
4. 事件结束后推进到下一事件或下一棒。

**不做**：走路、寻路、开战、战术演出、兵力结算、胜负判定、城池易主。这些全部复用现有代码。

### 3.2 状态机

```
idle
  └─ prepare(event)
       ├─ battle    → travel → battle → aftermath → advance
       └─ operation → travel → narrate → advance

advance
  ├─ 本事件还有 battles[] 下一场 → prepare(next battle)
  ├─ 下一事件同棒               → prepare(next event)
  ├─ 下一事件换棒               → relay(next lead) → prepare(next event)
  ├─ 下一段 status='ready'      → prepare(next segment)
  └─ 没有下一段                 → finish('segment-boundary') → 回落普通百岁自动寻将
```

**入口闸门**：`tick()` 第一行先判——

```ts
if (this.hero.autoPlan !== 'centenarian') return;  // 只跑百岁
if (!this.hero.autoMode) return;                   // 玩家关自动 = 导演暂停
if (this.deps.isScene13Active?.()) return;         // 战术中不推进
if (this.quest || this.hero.isAttached()) return;  // 手上已有事，不抢
```

`autoTravelToBestCity` 只有在「无任务、未随军」时才会被调到（`PlayerQuestSystem:3670`），所以导演不会抢玩家手动点的路。

### 3.3 与现有系统的接口（只加这些点）

| 位置 | 加什么 | 为什么 |
|---|---|---|
| `PlayerQuestSystem.tick`（3580 前） | `this.chronicle.tick()` | 每 400ms 推进；战术中自动跳过 |
| `autoTravelToBestCity`（3770 开头） | `const t = this.chronicle.nextTravelTarget(); if (t) { ...; return; }` | 编年史优先于「按城找将」 |
| `PlayerQuestSystem.startFirstBattle`（2156） | 新增 public `startChronicleBattle(event, step)` 包装 | 导演直接起兵，不走会面对话；复用现有起兵/行军/开战 |
| `beginClassicStrategicBriefing`（3909） | 编年史时 key 用 `event:${event.id}`，文案优先事件 `strategic`；非编年史仍用 `battleId` | 防重复、按事件念 |
| `finishGeneralEvent` / `cleanupFirstBattleState`（1699 / 2590） | `this.chronicle.onBattleEnded(...)` | 战斗结束推进下一场 |
| `GameAppCombatHooks`（325 / 332） | 在 `resolvedBattleBriefing` 计算前插 `const chronoTactical = app.playerQuest?.getChronicleTactical(battleId)`，优先于 `battleBriefing` | 战术段优先事件 `tactical` |
| `GameApp.jumpToYear`（1009） | 直接调用 | 换年现成入口，别另写 |
| `GameSaveManager`（155） | 存 `chronicle: { segment, eventIndex, stepIndex, phase, done }` | 读档续跑 |
| `GameConfig.TIME.TIMELINE_START_YEAR`（140） | -500 → -550（待定） | 否则第一段前 50 年被钳掉 |

`nextTravelTarget()` 返回三类之一，避免把「去据点/去坐标/追军团」三套逻辑揉进导演：

```ts
type ChronicleTarget =
  | { kind: 'city';    cityId: string; generalId?: string }   // 交给现有 travelToCity / 会面
  | { kind: 'general'; generalId: string }                    // 交给现有「认人不认城」追击
  | { kind: 'point';   lat: number; lng: number; label: string };
```

- `city` / `general` 走 `autoTravelToBestCity` 现有的「据点 → 会面 → 前线」分支；
- `point`（叙事事件的地点）：**未随军**时 `hero.travelToPoint(lat,lng,label,cb)`；**已随军**时复用 `marchHostToFirstBattle` 的军团寻路（`travelToPoint` 开头会挡「你正在军中」）。

### 3.4 五种相位

- **prepare**：`jumpToYear(event.year)` + `setSeason(event.season)`；解析 `place` / `cameraGeneralId`；起战略播报；算出 `nextTravelTarget`。
- **travel**：战斗事件 → 目标主角（或已存在的军团）；叙事事件 → 事件地点。距离 > 500km 或换棒 → 硬转场；否则走路。
- **battle**：调用 `startChronicleBattle`；等 `onBattleEnded`；赢了按史实推进，输了也推进（记 `deviation`），不重试、不卡死。
- **operation**：到达地点后，等战略段念完 → 念战术段（作为「行动过程」）→ `advance`；不进战术模式。
- **relay**：换棒时卸下旧军团/玩家、切到新主角；同城交接不换城；跨区交接用硬转场。

### 3.5 时间与转场

- **事件级跳年**：每个 `prepare` 把年份/季节对齐到事件；事件内让时钟自然走（60 游戏秒/年），打完下一事件再跳。
- **同棒内**：沿用现有军团与道路，连续行军；遵守 `路的规则`（>500km 设断点、起点=上一战落点、一镜到底）。
- **换棒/跨大区**：允许「史书翻页」硬转场；这是 `剧本工序` 里「换人＝换卷换线」的同一口径。转场只发生在**事件之间**，绝不发生在战斗内部。
- **开局第一个事件**：玩家现在随机出生，直接硬转到第一事件起点（或改 `setupPlayer` 的出生点为第一事件城外）；不许从随机出生点走几千公里。硬转场只改玩家/镜头位置，不改城池归属、不触发占城流程。

### 3.6 播报时序与优先级

优先级：

1. 编年史事件的 `strategic` / `tactical`
2. `CLASSIC_BATTLE_BRIEFINGS[battleId]` 的 `strategic` / `tactical`
3. `FIRST_BATTLE_STRATEGIC_BACKGROUNDS` / `FIRST_BATTLE_BACKGROUNDS`
4. `fallbackStrategicLine`

规则：

- 战略段在 `prepare` 开口，赶路/转场/城下对峙期间念完；到点没念完，战斗事件就地驻足（`onHostReachFirstBattle` 已做）。
- 战术段在进战术模式时由 `Scene13WarLayer` 念；叙事事件在到达地点、战略段念完后念。
- 同一事件只念一套；多场战斗时 `briefing: 'event'` 只给第一场，其余用各自战斗文案或跳过。
- 手动改目标/暂停 → `stopAfterCurrent()`；不抢话、不叠音。

### 3.7 容错（绝不卡死）

| 故障 | 处理 |
|---|---|
| 地点解析不了 | 跳过该事件，记 `skipped`，下一事件继续 |
| 主角缺库 | `cameraGeneralId` 代理；没有代理 → operation |
| 战斗数据缺 | 降级 operation，不硬造战斗 |
| 寻路失败/军团丢失 | 硬转场到事件起点，重试一次；再失败跳过 |
| 战败 | 记 `deviation`，推进；编年史是史书，不因玩家输赢停摆 |
| 读档 | 从保存的事件起点重跑；同一事件文案可能重念一次，可接受 |
